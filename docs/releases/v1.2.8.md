# v1.2.8 — Sync the clock at boot / 开机自动校时

简体中文 · English

## 简体中文

**入口：** 已有安装更新使用 `bash install.sh --update --release v1.2.8`；首次安装见 [本版本安装教程](https://github.com/wgltony/U60Pro-OpenUI/blob/v1.2.8/docs/INSTALL.zh.md)。本版本只改动 agent（网页、触摸屏程序、lpac、mihomo 与 v1.2.7 相同），安装流程与 v1.2.7 相同。

1. **开机自动校时：** 设备没有带电池的实时时钟，OpenWrt 自带的 NTP 客户端默认关闭。接在 Wi-Fi 中继上时也没有蜂窝网络授时，所以重启后系统时间会退回到很早（实测 2025 年）。时间不对会让所有 TLS 连接失败——最明显的是 Tailscale：它连不上控制服务器，报“未登录”，一直离线。本版本让 agent 自己校时：
   - 在启动 Tailscale **之前**、也独立于 Tailscale，在后台校时，所以不开 Tailscale 时时间也会被校正。
   - 时间取自国内站点的明文 HTTP `Date` 响应头（通过 `/usr/bin/curl` 请求 `http://www.baidu.com` 等）。明文 HTTP 不做证书校验，时间错也能取到；Clash 对国内域名走直连，代理的 120 秒时间偏差校验也挡不住它。
   - 系统时间偏差超过 30 秒时用 `settimeofday` 校正，时区保持不变。开机后每 10 秒重试一次直到第一次成功（中继的联网可能还没就绪），之后每小时复查一次。

**验证范围：**
- fmt、clippy（`-D warnings`）与 aarch64 交叉构建均通过；新增模块带单元测试。完整测试套件由 CI 的检查任务运行。
- 实机（U60 Pro，B31）模拟了一次重启：把系统时间设成 2025 年后重启 agent，使其在错误时间下启动。日志记录到 `[clock] set from HTTP Date (was off by 58648261s)`，4 秒后 Tailscale `Running online`，中继与联网保持正常，电脑经 tailnet 直连设备。部署方式是替换 agent 二进制并保留备份，不是经 `install.sh` 全新安装。
- **未在实机验证：** 真正的冷启动（本次为模拟重启而非断电冷启）、以及完全没有任何可达授时站点时的表现。

## English

**Entry point:** update an existing installation with `bash install.sh --update --release v1.2.8`; for first installs see the [versioned install guide](https://github.com/wgltony/U60Pro-OpenUI/blob/v1.2.8/docs/INSTALL.md). This release changes only the agent (the web panel, touchscreen binary, `lpac` and `mihomo` are the same as v1.2.7); installation is the same as v1.2.7.

1. **Sync the clock at boot:** the device has no battery-backed real-time clock, and OpenWrt's own NTP client is disabled. On the Wi-Fi relay there is no cellular time either, so after a reboot the system clock falls back to the distant past (seen: 2025). A wrong clock breaks every TLS connection — most visibly Tailscale, which cannot reach its control server, reports "not signed in", and stays offline. The agent now sets the clock itself:
   - It runs **before** Tailscale and independently of it, in the background, so the clock is corrected even when Tailscale is off.
   - The time comes from a domestic site's plain-HTTP `Date` response header (`/usr/bin/curl` to `http://www.baidu.com` and fallbacks). Plain HTTP does no certificate check, so a wrong clock cannot block the fetch, and Clash routes `cn` names DIRECT, so the proxy's 120 s skew check cannot block it either.
   - When the system clock is off by more than 30 s it is corrected with `settimeofday`, leaving the timezone untouched. After boot it retries every 10 s until the first success (the relay's uplink may not be up yet), then re-checks hourly.

**Validation boundary:**
- fmt, clippy (`-D warnings`) and the aarch64 cross build all pass; the new module ships with a unit test. The full test suite runs in CI's checks job.
- On a real U60 Pro (B31) we simulated a reboot: set the clock to 2025 and restarted the agent so it started with the wrong clock. The log recorded `[clock] set from HTTP Date (was off by 58648261s)`, Tailscale went `Running online` 4 s later, the relay and internet stayed healthy, and a Mac reached the device directly over the tailnet. Deployment replaced the agent binary with a backup kept; it was not a fresh `install.sh` installation.
- **Not checked on the device:** a true cold boot (this was a simulated restart, not a power-off), and behaviour when no time source is reachable at all.
